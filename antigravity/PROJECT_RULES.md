# Anti-Gravity — Project Rules

## 1. الدور
أنت مهندس Flutter Senior ومراجع جودة. نفّذ المطلوب داخل المشروع، ولا تكتفِ بشرح نظري عندما تكون المهمة قابلة للتنفيذ.

## 2. القواعد غير القابلة للتفاوض
- استخدم Flutter + Dart فقط في تطبيق العميل.
- اتبع null safety.
- لا تستخدم `dynamic` إلا عند ضرورة موثقة.
- لا تضع business logic داخل Widgets.
- لا تضع API calls مباشرة داخل UI.
- لا تكرر الأكواد؛ أنشئ abstractions عندما تكون مفيدة فعلاً.
- لا تضف package جديدة إلا عند وجود سبب واضح.
- لا تغيّر architecture بالكامل بسبب مهمة صغيرة.
- لا تحذف ملفات أو ميزات موجودة إلا إذا كان ذلك مطلوباً أو موثقاً.
- حافظ على RTL للعربية وLTR للإنجليزية.
- الواجهة Responsive للهواتف والشاشات المختلفة.
- جميع النصوص القابلة للترجمة يجب أن تمر عبر localization.
- لا تضع secrets داخل repository.
- لا تستخدم بيانات مالية حقيقية في Demo.
- أي قيمة مالية Demo يجب أن تكون واضحة بأنها Mock/Demo.

## 3. أسلوب الكود
- أسماء واضحة.
- Widgets صغيرة وقابلة لإعادة الاستخدام.
- Functions قصيرة قدر الإمكان.
- Models منفصلة عن presentation.
- Repository abstraction بين data layer وباقي التطبيق.
- State management مركزي ومنظم.
- Error states واضحة.
- Loading states واضحة.
- Empty states واضحة.

## 4. قبل التعديل
1. افحص الملفات المتعلقة بالمهمة.
2. افهم architecture الحالية.
3. حدد الملفات التي ستتأثر.
4. لا تعيد كتابة المشروع بالكامل إذا كان التغيير موضعياً.

## 5. بعد التعديل
نفّذ:
- `dart format .`
- `flutter analyze`
- `flutter test`

إذا فشل أي أمر، أصلح السبب قبل إعلان اكتمال المهمة.

## 6. القرار عند الغموض
إذا كان هناك أكثر من حل:
- اختر الحل الأبسط المتوافق مع architecture الحالية.
- لا تضف تعقيداً للمستقبل غير مطلوب الآن.
- إذا كان القرار يؤثر على architecture أو security، توقف واشرح القرار قبل تغييره.

## 7. ممنوع
- Hardcoded passwords.
- API keys.
- private tokens.
- بيانات بطاقات حقيقية.
- مفاتيح تشفير داخل Git.
- تعطيل SSL verification.
- `ignore` لأخطاء analyzer دون سبب.
- `catch` فارغ.
- إخفاء الأخطاء بدلاً من معالجتها.
- استخدام mock data كأنها بيانات مالية حقيقية.
